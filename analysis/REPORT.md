# LaminaDB 常驻内存 → 按需数据页：可行性评估

结论先行：**不建议现在把版本链迁到按需数据页。** 在当前源码里，页驻留能解决的问题（内存占用）只占实测差距的一小部分；
真正的扩展性墙是逐次写入/提交的全表复制、索引构建的二次复杂度、128 MiB 检查点上限、查询持有排他锁、以及日志记录全量常驻。
这五项里没有一项会因"把行放到页里"而消失，其中若干项还会因为多了一层写回而变糟。

本报告不实施迁移；所有数字来自本仓库源码 + 两个有界原型（`analysis/` 下），可复现。

---

## 1. 当前实现的事实归属（源码）

| 事实 | 位置 | 现状 |
| --- | --- | --- |
| 版本链全部常驻 | `internal/versions/store.go:16-18` | `map[relation]map[key][]Version`，每版本存完整 `datum.Row` |
| 读取可见性 | `internal/versions/store.go:32-47` | 链内二分找 `seq <= at` 的最后一版 |
| 回收保留锚点 | `internal/versions/vacuum.go:15-26` | 每键保留"水位处及其后"的版本；若末尾是水位前墓碑则整链删除 |
| 每次 Put 全表扫描 | `internal/engine/transaction.go:80` | `d.store.Scan(table, tx.Snapshot)` 复制整表再 overlay |

| 候选数取内存键数 | `internal/engine/read.go:44` | `len(d.store.Tables[rel])` 作为 `plan.candidates` 基数 |

## 2. 实测：常驻内存到底花在哪

环境：Linux/arm64、Go 1.25、16 GiB、单机；合成 4 列 relation（int 主键 + 64 B 文本 + int + bool）。

| 数据 | 结果 |
| --- | --- |
| 真实引擎，每版本堆开销 | **722–781 B/版本**（14–16 B 文本） |
| 原型紧凑编码，每版本 | **78.6 B/版本**，堆上约 **71 B/版本** |
| 日志内存副本 | **752 B/版本**；盘上仅 **166 B/版本** |
| 1M 版本冷启动 | 6.2 s / 1.82 GiB RSS（160 MB journal） |
| 2M 版本冷启动 | 11.6 s / 2.76 GiB RSS |
| 5 万版本冷启动 | 0.6 s / 169 MiB RSS |

也就是说：**同一份数据，换成紧凑行表示就能拿到约 10× 的内存收益，且不需要任何 I/O 或恢复协议改动。**
把历史行放到页里，最好的原型也只把常驻降到约 1/30（1.0 MiB 页元数据 + 缓存），但这是在已经用紧凑表示的前提下。
先做表示，再做分页，收益是相乘的；只做分页，等于把 700 B/版本的问题变成"700 B × 命中的版本"。

## 3. 实测：真正的扩展性墙（与页缓存无关）

| 操作 | 1k 键 | 10k 键 | 100k 键 |
| --- | --- | --- | --- |
| Put（含一次全表 Scan） | 0.3–0.5 ms | 3.7–6.0 ms | 70–95 ms |
| Commit（唯一性全表 Scan） | 3.6–5.2 ms | 11–18 ms | 88–137 ms |

- **索引构建是二次的**：1M 个不同候选（值,键）时实测 **404–476 s**、约 185 MB，且在 `d.mu.Lock()` 内。
  2M 版本的实例通过 HTTP 建单列索引，584 s 未返回、进程随后消失。
  vacuum 也走同一条 `index.Build`，所以"回收"在有索引时会变成一次长阻塞。
- **检查点有硬上限**：1M 版本 × 64 B 文本 → 镜像 144 MB > 128 MiB，`POST /checkpoint` 永远返回
  `503 checkpoint exceeds image limit`（耗时 3.2 s 后才失败）。同数据 32 B 文本可写 108 MB 镜像，但
  重启从 6.1 s / 1.92 GiB **变慢到** 11.2 s / 2.76 GiB——检查点在此规模下既不能替代日志，也救不了启动。
- **查询串行化**：`Query` 持写锁，一次宽历史扫描期间提交全部排队。
- **日志双份常驻**：`w.Records` 与版本链同时存在，内存等于两份历史。

这些是分页迁移**不会**改善的部分；其中索引与检查点还会因"页上数据需要重建"而更贵。

## 4. 有界原型：三种驻留方向，同一语义校验

原型 `analysis/paging`：50k 键 × 8 轮 + 热点 8 轮 = 440k 版本，紧凑编码 34.6 MB，16 KiB 页，缓存 2 MiB。
每种布局都与"全常驻"在**同一快照规则**下逐键逐位置比对：

```
VERIFY keys=50000 seqs=17 mismatches=0
SEQSCAN at=1/8/16 want=50000 got=50000 missing=0 extra=0
```

| 布局 | 常驻堆 | 点查 20k | 混合 20k点+2k范围+3宽扫 | 3 次宽扫 | 写放大 |
| --- | --- | --- | --- | --- | --- |
| 全常驻（基线） | 31.4 MB | 13 ms | 409 ms | 41 ms | 0（内存） |
| 定位表 + 追加历史文件 | 19.0 MB* | 11 ms | 468 ms | 242 ms | 1.00× |
| 定位表 + 当前行常驻 | 19.0 MB* | 8 ms | 469 ms | 309 ms | 1.00× |
| 键序页 + 稀疏索引 | 1.0 MB | 435 ms | 1088 ms | 164 ms | **209×**（就地重写）/ 1.00×（增量） |
| 当前行常驻 + 键序页 | 1.0 MB+当前集 | 97 ms | 752 ms | 229 ms | — |

\* 含 8 MiB 行缓存；目录本身约 11 MB。定位表实测 13.4 MB/440k 版本。

关键读放大（同一 34.6 MB 语料）：

| 页大小 | 缓存 | 混合负载读取量 |
| --- | --- | --- |
| 4 KiB | 2 MiB | 32 MB（3×） |
| 16 KiB | 2 MiB | **454 MB（13×）** |
| 64 KiB | 2 MiB | 228 MB（23×，语料仅 10 MB） |

写路径（200 次提交 × 200 写 = 40k 新版本，逻辑 3.15 MB）：就地重写页 **659 MB / 1256 ms**，追加式增量 **3.15 MB / 68 ms**。

**结论**：页布局只有在"追加写、小页、且只服务稀有历史读"时成立；一旦追求键序就地更新或大页，会被自身测量推翻。

## 5. 恢复责任与状态归属

迁移后每条事实必须只有一个所有者，且重启与在线路径走同一解释器：

| 事实 | 现在 | 分页后的所有者 | 恢复责任 |
| --- | --- | --- | --- |
| 可见行 | 内存链 | 同样由 `Visible` 决定，但数据可能不在内存 | 启动必须能从日志/历史文件重建"每键锚点"，且 `at=horizon` 可读 |
| 版本链锚点 | `Vacuum` 保留 | 必须显式持久化"水位锚点"，不能依赖页是否在缓存 | 回收记录 + 锚点缺失 → 拒绝启动，而非静默返回空 |
| 墓碑 | 链尾 Deleted | 同上；**墓碑必须与保留锚点同生命周期** | 删键后若墓碑被回收而旧版本仍在，会"复活" |
| `plan.candidates` | `len(Tables[rel])` | 必须来自持久化键目录，不能是驻留键数 | 否则统计含义静默变化 |
| 索引候选 | 全历史内存树 | 需持久化或可从历史重建 | 重建耗时必须可接受（现在 1M 候选 = 400 s） |
| 检查点 | 全量 JSON ≤128 MiB | 应改为"引用历史文件 + 校验摘要"，而非内嵌所有版本 | 摘要必须覆盖被引用的所有段 |

原型里真实踩到过第 3 行：最初的"当前行常驻 + 页历史"在键被删除后，常驻表只删了当前行、没有保留墓碑，
读取会穿透到页里的旧版本，摘要比对立刻不一致（`VERIFY_MISMATCH`）。这正是"同一提交位置必须解释为同一行"的失败模式，
且它不会表现为崩溃，只会表现为历史读返回旧值。

## 6. 公开入口的等价性探针

`analysis/equiv/`（只走 HTTP）：

- 检查点 → 重启：保留区间内 9 个位置，行内容 **9/9 完全一致**。
- 回收后：水位处行集合不变（21/21），但 `plan.candidates` 从 41/40 变为 38/38——
  **行不变，执行事实会变**。这说明 `candidates` 是执行事实而非存储不变量，迁移时必须给它一个持久来源。
- 长读事务钉住旧快照：requested horizon=19 时实际 horizon=9，`pinned=true`，40 个键保留 **438 个版本（10.95/键）**；
  释放读者后再回收，降到 **40 个版本（1.0/键）**。

## 7. 建议（可被负载反例推翻）

**方向：A（定位表 + 追加历史 + 当前行常驻），不做就地更新的键序页。**

分阶段，按证据推进：

1. **先做表示与所有权修复（收益最大，不涉及分页）**
   - 行改为紧凑结构（去掉 `map[string]Value`），目标 ≤120 B/版本 → 约 6–10× 内存收益（实测 722 → 71 B）。
   - `Put`/`Commit` 去掉全表 `Scan`，改用按键读 + 索引做唯一性检查（实测 100k 键时 70–137 ms/次）。
   - 索引改增量维护，禁止 vacuum 整表重建（1M 候选 400 s → 目标 <1 s 摊销）。
   - 检查点改为"引用历史段 + 摘要"，解除 128 MiB 硬上限与"检查点反而拖慢启动"。
   - 日志记录改为可分页（`w.Records` 不再全量常驻）。

2. **再做按需驻留（本报告评估的部分）**
   - 只对**超过保留锚点**的历史版本分页；当前行与锚点常驻。
   - 写路径只允许追加（增量段），不做就地页重写。
   - 页大小按工作集选择，建议 4–8 KiB；页元数据必须常驻。
   - 历史顺序扫描用独立稀疏页索引，不要逐键点读。

**推翻本建议的负载反例（任一成立则应改为全常驻或重新设计）：**

| 反例 | 判据（实测已给出依据） |
| --- | --- |
| 历史读占比高（>25%）| 混合负载已从 409 ms 升到 469 ms；占比再高时点读缓存被冲掉 |
| 短查询不窄，常见全表投影 | 宽扫 41 ms → 242 ms（追加历史）/ 309 ms（当前行常驻）|
| 写多且小、键随机 | 就地页重写 209× 写放大、1256 ms vs 68 ms；只有追加式可行 |
| 页缓存 < 工作集 1/10 | 16 KiB 页在 2 MiB 缓存下读放大 13×；64 KiB 页 23× |
| 长事务频繁钉住旧水位 | 实测 10.95 版本/键被保留，回收几乎不前进；此时页缓存与保留空间互相挤压 |
| 恢复时间要求 < 数秒 | 1M 版本已 6.2 s；加检查点反而 11.2 s |

**不建议做的：**

- 不要用 mmap/OS 页缓存当"无限内存"：常驻键目录仍随键数线性增长（440k 版本 13.4 MB），而且容器内页缓存计入内存预算，无法按查询预算。
- 不要把"当前行写回文件"当作迁移完成：那会让历史读、唯一性检查、索引候选、`plan.candidates` 各自拥有不同来源。
- 不要在索引仍为二次构建的情况下引入分页：vacuum 会同时触发页回收与索引重建，两者都在写锁内。

## 8. 复现

```sh
export PATH=<go1.25>/bin:$PATH
go build -o bin/laminad ./cmd/laminad

# 真实引擎：内存、提交、重启、检查点上限、索引重建
MEM=1 go run ./analysis/enginecost      # 722-781 B/版本
VAC=1 go run ./analysis/enginecost      # 检查点上限、带索引回收
go run ./analysis/enginecost            # Put/Commit 随表规模
go run ./analysis/indexscale            # 索引构建二次增长
LIMITS=1 go run ./analysis/measure      # 128 MiB 镜像边界

# 有界原型：四种布局 + 逐键逐位置语义校验 + 写放大
go run ./analysis/paging -keys 50000 -revs 8 -hot 8 -text 64 -page 16 -cache 2
go run ./analysis/paging -mode writes -keys 20000 -revs 6 -hot 4 -text 64 -page 16 -cache 8

# 公开入口等价性（检查点/重启/回收/钉住）
python3 -I analysis/equiv/equiv.py --binary bin/laminad
python3 -I analysis/equiv/horizon.py
```

## 9. 局限

- 原型是单线程、内存内 LRU、无并发；真实引擎每次查询持排他锁，所以原型的延迟差是**乐观**下界。
- 读取量按 `ReadAt` 字节计，未剥离 OS 页缓存命中；本机缓存未被主动清空，跨进程冷读会更差。
- 合成数据为 4 列、文本 ≤64 B；`datum.Row` 的 map 开销在列数更多时更不利，紧凑表示的收益会更大。
- 1M/2M 版本的索引构建与检查点数字来自本机 16 GiB 的完整运行或崩溃前的观测，未做 GC 调优。
